# 改善TODO（2026-09-04 起票）

> ## ✅ 決着した回帰（2026-09-04）
>
> **症状だった**: バトルで敵を1体倒すと、次の敵が出てこないまま画面が止まる。
>
> **原因**: ゲーム側のロジックの誤りではなかった。
> 撃破後の進行を握る `waitForDefeatAnimationThen` が、撃破演出の残りフレームが
> 0 になるのを **requestAnimationFrame だけで待っていた**。ブラウザは画面が
> 見えていない間フレームを止めるので（タブが裏に回る・別のアプリに切り替える・
> 端末がスリープする）、倒した直後にそうなると演出が終わらず、次の敵が出ない。
>
> **切り分けの経緯**: 確認に使っていたブラウザのタブが裏に回っていたため、
> rAF が止まって「止まったように見える」状態が再現していた。
> フレームが確実に回る状態（MessageChannel で rAF を回す一時パッチ）にして
> 同じ手順をやり直すと、敵を続けて2体倒しても `currentEnemyIndex` が 0→1→2 と
> 正しく進み、例外も出なかった。**13コミットのどれにも原因は無かった。**
>
> **対処** (`c99f48e`): 実時間2秒（演出は約1秒）の締め切りを足し、フレームが
> 来なくても必ず先へ進むようにした。教室のiPadで子どもが一瞬ホームに戻っても、
> 戻ってきた時に止まったままにならない。
>
> **調べ方の注意（次に同じ落とし穴にはまらないため）**
> - **ブラウザ拡張から操作するタブは、裏に回ると rAF が止まる。**
>   アニメーションの完了を待つ処理は、それだけで「フリーズ」に見える。
>   `document.visibilityState` を最初に確認すること。
> - 拡張の `javascript_tool` から `import()` したモジュールは**別インスタンス**になる
>   （`gameState` を import しても、アプリが使っている方とは別物）。
>   状態を見たい時は、アプリ側から `window` に置いたものを読むこと。
>   一方、**DOM と `window` の読み書き自体はページと共有されている**ので、
>   `window.fsm.change('画面名')` で画面を飛ばす、といった操作は確実に効く。

## 各項目の根拠（調査結果）

### A-1
`public/assets/` の全トップレベルを機械照合したところ、コードから参照されるのは
`images` と `audio` の2つだけ（`grep -rhoP "assets/[^'\"\`\s\)]+"` → images 59 / audio 52、他ゼロ）。
残り13ディレクトリ 1,950MB は制作時の中間素材。Vite は `public/` を丸ごと `dist/` に
コピーするため、毎回のデプロイに乗っている。

### A-2
答え合わせは完全一致（`battleScreen.js:4548` / `utils/readings.js`）。カタカナ→ひらがなと
トリムしかしないため、「きよう（→きょう）」「ぢ/じ」「づ/ず」「濁点忘れ」が
`recordKanjiAnswer(id, false)` で誤答として学習記録に残り、SRSにも乗る。
**読めているのに打てなかった子が、読めない子として記録される。**

### A-3
`inputmode="kana"` はHTML仕様に無い値（有効値は none/text/tel/url/email/numeric/decimal/search）。
ブラウザは無視するので、その端末で最後に使われたキーボードが出る。
`battleScreen.js:880, 2567` / `practiceBattleScreen.js:350`。
50音パッドを自前で持てば、`battleScreen.js:2480-2560` の visualViewport 補正の山も不要になる。

### A-4
`speechSynthesis` の使用箇所はゼロ。追加依存なしで ja-JP が使える。
音声合成はユーザー操作の流れの中でしか始められない（Chrome で not-allowed を確認）ため、
BGMの自動再生対策と同じ「最初のタップ」で解錠している。
**実際に声が出るところは教室のiPadでの確認が要る。**

### A-5（作業中に発見）
PWA撤退時に sw.js を消したが、SPA の rewrite により /sw.js は 404 ではなく index.html を
200 で返すため、古いSWの登録が消えない。cache-first で古い index.html が配られ続け、
その端末には新しい版が永遠に届かない。手元のブラウザで実際に再現した
（古い main.js が配られ、タイトルも旧「漢字バトルゲーム」のままだった）。
自己消去型の sw.js を置き直して復旧を確認済み。

### B-1
出題は `battleScreen.js:5470` で一様ランダム＋直近バッファ除外のみ。
さっき読めなかった字がそのステージ中に二度と出ないことが普通に起きる。
`gameState.kanjiAnswerStats`（既存の正史）で重み付けできる。データ変更は不要。

### B-2
単漢字を出して**どの読みでも正解**（`getReadings()` の全候補と照合）。
「生」は せい/しょう/なま/き のどれでも通るため、知っている1つの読みだけで進めてしまう。
例文データ `examples` は小1の80字にしか無い（他学年0件）ことを確認済み。

### B-3
`public/data/proverbs_final_400.json` と `proverbs_with_monsters.json`（読み・意味・例文つき、
モンスター紐付け版まである）が `src/` から一切参照されていない。

### C-1
セーブは `krb_save` 単一スロット（`core/saveData.js:6`）＋匿名認証。
同じ端末を2人目が使うと1人目の記録の上に書かれる。

### C-2
`kanjiAnswerStats` に漢字別の正誤が全部あるが、外に出す手段が無い。

### C-3
授業の残り時間で切り上げると「途中でやめた」形になる。
チェックポイント（`BATTLE_CHECKPOINT_AT`）の仕組みが流用できる。

### D
引き継ぎ書「5. 未決定事項」の色弱モード・フォントサイズは**実装**を推す。
対象が「漢字が苦手な子」である以上、視覚特性で弾かれる子を作るのは設計思想と矛盾する。
自動ルビは、監査②の「UIの配当外漢字126箇所」と「図鑑テキストが低学年に読めない」を
表示側の1機能で同時に解ける可能性がある。
