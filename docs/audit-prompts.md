# 監査プロンプト集

ヨミタビの品質を上げるために、AI に監査を依頼するときのプロンプト。
「クオリティを上げて」を1本で投げると当たり障りのない一般論か大規模リライトが返ってくるため、**目的別に分けて**投げる。

最終更新: 2026-08-28

---

## 使い方

1. リポジトリを読める状態（`C:\kanji-game-latest`）で AI を起動する
2. 下のプロンプトを**そのまま**貼る
3. **①の結果を見てから②③に進む**。同時に投げると指摘が重複し、精度も落ちる

投げる順の推奨は **① → ② → ③**。
①を最優先にする理由: これまで見つかった隠れバグ5件（SP使用不能・復習画面クラッシュ・名前入力ソフトロック・北海道BGM無音・世界編BGM無音）は**全て同じ型**だった ―― 機能は作ってあるのに静かに壊れていて、エラーすら出ない。今の段階では「作る」より「繋ぎ直す」ほうが体験の改善効率が高い。

## 依頼
同じ型の「静かに壊れている箇所」を、コード全体から洗い出してください。観点:
1. 到達不能な画面・機能 — 実装済みだが、どの画面からも遷移できない

4. 効かない設定 — 設定画面のトグルが実挙動に繋がっていない
5. 保存されない進捗 — 画面には出るが `krb_save` に永続化されていない値

## 禁止事項
- 今回はコードを修正しない。報告だけ（直す順番は開発者が決める）
- npmパッケージを追加しない（devDependenciesはviteのみ）
- git履歴を触る操作をしない（.gitが6.7GBある）
- battleScreen.js(6,240行)のリファクタ提案はしない。別途計画済み

## プロンプトの型（新しく書くとき）

上の3本は全てこの5要素でできている。使い回せる。

| 要素 | このプロジェクトでの中身 |
|---|---|
| **入口の指定** | 「まず `docs/progress-handoff.md` を読む」。この1行で背景説明が丸ごと不要になる |
| **具体例で範囲を示す** | 「こういうバグが実際にあった」と過去の実例を並べる。抽象的な観点リストより効く |
| **証拠の基準** | 「`ファイル名:行番号` と、実行したコマンドの出力を添えろ」「確認済みと疑いを分けろ」。**これが無いと、もっともらしい作り話が混ざる** |
| **禁止事項** | 修正するな / 依存を足すな / git履歴を触るな / battleScreen をリライトするな |
| **優先度の判断軸** | 「技術的深刻度ではなく、子どもの体験が何を失うかで並べろ」 |

### 入れてはいけないもの

- 「全体的に良くして」「クオリティを上げて」 → 範囲が無限になり、浅い指摘が並ぶ
- 出力形式の指定なし → 長文のエッセイが返り、次の一手に繋がらない
- 修正まで許可する → 大規模リファクタを勝手に始め、動いていたものが壊れる。**まず報告だけ**にして、直す順番は開発者が決める
