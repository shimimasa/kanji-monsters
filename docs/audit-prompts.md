# 監査プロンプト集

ヨミタビの品質を上げるために、AI に監査を依頼するときのプロンプト。
「クオリティを上げて」を1本で投げると当たり障りのない一般論か大規模リライトが返ってくるため、**目的別に分けて**投げる。

最終更新: 2026-08-28

---

## 使い方

1. リポジトリを読める状態（`C:\kanji-game-latest`）で AI を起動する
2. 下のプロンプトを**そのまま**貼る
3. **①の結果を見てから②③に進む**。同時に投げると指摘が重複し、精度も落ちる

投げる順の推奨は **① → ② → ③**。
①を最優先にする理由: これまで見つかった隠れバグ5件（SP使用不能・復習画面クラッシュ・名前入力ソフトロック・北海道BGM無音・世界編BGM無音）は**全て同じ型**だった ―― 機能は作ってあるのに静かに壊れていて、エラーすら出ない。今の段階では「作る」より「繋ぎ直す」ほうが体験の改善効率が高い。

## ① 壊れた配線の全数監査（最優先）

```
あなたは「ヨミタビ」という小学生向け漢字学習ゲームのコードベースを監査します。

## 最初にやること
`docs/progress-handoff.md` を読んでください。前提・ブランチ規約・これまでの経緯・
未決定事項が全てそこにあります。推測で背景を補わないでください。

## 背景
- プレイヤー: 漢字が苦手で、自尊心が脆弱な小学生
- 開発者は小学校教員の単独開発。実際に教室で使う
- このプロジェクトの最大の問題は「機能が足りないこと」ではなく
  「作った機能が静かに壊れていること」。実際に見つかった例:
  - 世界ステージのBGMが全滅（音源ファイル名だけ先頭大文字だったのに、
    小文字のstageIdからURLを組み立てていた。SPAのrewriteで404ではなく
    index.htmlが200で返るため、コンソールにエラーすら出なかった）
  - スキルポイントが一切使えなかった（status画面がどこからも到達できなかった）
  - 「今日の復習」画面がTypeErrorでクラッシュ
  - 起動時に前回ステージが別IDで上書きされる

## 依頼
同じ型の「静かに壊れている箇所」を、コード全体から洗い出してください。観点:
1. 到達不能な画面・機能 — 実装済みだが、どの画面からも遷移できない
2. 参照先が存在しないアセット — 画像/音声/データへの参照で、実ファイルが無い or 名前がずれている
3. 握りつぶされた例外 — try/catch や `?.` で失敗が黙って隠れ、子どもには「何も起きない」に見える
4. 効かない設定 — 設定画面のトグルが実挙動に繋がっていない
5. 保存されない進捗 — 画面には出るが `krb_save` に永続化されていない値

## 証拠の基準（最重要）
- 推測で書かない。1件ごとに `ファイル名:行番号` と、
  **実際に実行したコマンドとその出力**を添える
- 例（世界編BGMバグを特定した実際の手口）:
  `npm run build && npx vite preview` した上で
  `curl -s -o /dev/null -w '%{http_code} %{content_type}' http://localhost:4173/assets/audio/asia_area3_b.ogg`
  → `200 text/html` が返る（音源ではなくindex.htmlが返っている）ことを確認
- 「確認済み」と「疑いがあるが未確認」を明確に分ける。未確認のものは確認方法も書く
- 見つからなければ「無い」と書く。件数を埋めるために弱い指摘を混ぜない

## 禁止事項
- 今回はコードを修正しない。報告だけ（直す順番は開発者が決める）
- npmパッケージを追加しない（devDependenciesはviteのみ）
- git履歴を触る操作をしない（.gitが6.7GBある）
- battleScreen.js(6,240行)のリファクタ提案はしない。別途計画済み

## 出力形式
重大な順の一覧表＋各件の詳細。重大さは技術的深刻度ではなく
**「これが壊れていると、子どもの体験が何を失うか」**で判断すること。
（例: SP使用不能 → 育成の報酬が丸ごと消える／BGM無音 → 世界編だけ手触りが貧しい）
```

## ② ポジティブフレーミング監査（体験の質）

```
## 最初にやること
`docs/progress-handoff.md` と `docs/claude Opus4.6-review.md`
（心理的安全性の設計思想＝このゲームの正史）を読んでください。

## 依頼
プレイヤーは「漢字が苦手で、自尊心が脆弱な小学生」です。
**「できなかった瞬間に子どもが傷つかないか」**がこのゲームの唯一の設計基準です。

子どもの目に触れる全てのテキストと演出を洗い出し、この基準で点検してください:
- UI文言、メッセージ、ボタンラベル、実績名、エラー表示、残っている alert()
- 間違えた直後・負けた直後・進捗が遅い時に、画面に何が出るか
- 効果音と色（誤答時に赤や不快音を使っていないか）

## 観点
1. 失敗を「情報」ではなく「評価」として突きつけていないか（「しっぱい」「まちがい」「×」）
2. 他者比較・順位・正答率の露出
3. UI自体に、その学年では読めない漢字を使っていないか（対象は漢字が苦手な子）
4. 詰まった時に必ず逃げ道があるか（1タップで練習へ避難できる等）
5. 押しても何も起きないボタン

## 守ってほしいこと
- 修正はしない。指摘と**代替文言の具体案**をセットで出す
- 1件ごとに `ファイル名:行番号` と実際の文言を引用する
- **既に良く出来ている箇所も挙げる**（何を壊してはいけないかを知りたい）
```

```
`docs/progress-handoff.md` を読んだ上で、このゲームを
**漢字ドリルではなく学習教材として**評価してください。

- `src/models/reviewQueue.js`（SM-2）の間隔設定は、
  週2〜3回しか触らない小学生の利用実態に合っているか
- ステージ内の出題順・出題数（1ステージあたり何問か）は、
  集中が続かない子に対して長すぎないか

- 「はじめて読めた漢字」「こんしゅうのがんばり」は、
  伸びが遅い子にとっても機能するか（伸びない週に何が表示されるか）

コードとデータ（public/data/*.json）を実際に読んで、数値を挙げて論じること。
一般的な学習理論の解説は不要。このゲームの実装に対する指摘だけ書いてください。
```

## プロンプトの型（新しく書くとき）

上の3本は全てこの5要素でできている。使い回せる。

| 要素 | このプロジェクトでの中身 |
|---|---|
| **入口の指定** | 「まず `docs/progress-handoff.md` を読む」。この1行で背景説明が丸ごと不要になる |
| **具体例で範囲を示す** | 「こういうバグが実際にあった」と過去の実例を並べる。抽象的な観点リストより効く |
| **証拠の基準** | 「`ファイル名:行番号` と、実行したコマンドの出力を添えろ」「確認済みと疑いを分けろ」。**これが無いと、もっともらしい作り話が混ざる** |
| **禁止事項** | 修正するな / 依存を足すな / git履歴を触るな / battleScreen をリライトするな |
| **優先度の判断軸** | 「技術的深刻度ではなく、子どもの体験が何を失うかで並べろ」 |

### 入れてはいけないもの

- 「全体的に良くして」「クオリティを上げて」 → 範囲が無限になり、浅い指摘が並ぶ
- 出力形式の指定なし → 長文のエッセイが返り、次の一手に繋がらない
- 修正まで許可する → 大規模リファクタを勝手に始め、動いていたものが壊れる。**まず報告だけ**にして、直す順番は開発者が決める

### ①の所見（次に②を投げる時の参考）

- **効いた指示**: 「実行したコマンドとその出力を証拠に添える」。報告に `node` スクリプトと `curl` の実測が付いてきたので、こちらの裏取りが速かった
- **足りなかった指示**: 「同じ根本原因が他にも波及していないか数えろ」。①は四国・九州のモンスター画像だけを指摘したが、実際は**110体中100体**が同じ原因で壊れていた。次回は「見つけた不具合ごとに、同じ原因の全件数を数える」を証拠の基準に足す
- **精度**: 裏取りした6件はすべて事実。誇張・作り話は無かった
